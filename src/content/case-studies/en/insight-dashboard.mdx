_Insight Dashboard is a module of the healthcare supply chain platform. It lets users view spend reports and analyze purchasing for each hospital organization._

## Problem

Insight Dashboard has 10 purchasing reports. Each one joins several tables and aggregates across many filters: period, corporation, department, vendor and item. The dashboard needed 40+ seconds to show all of its data, too slow for daily work.

Scale: <Metric>19+</Metric> US hospitals, <Metric>50M+</Metric> records processed daily, about <Metric>5,000</Metric> daily users. I work on it as a full-stack engineer in a team of three.

## Approach & alternatives considered

1. **Measure first.** I ran `EXPLAIN ANALYZE` on each slow query to see whether the query itself or a missing index was the problem.
2. **Pick the engine by access pattern.** The reports are read-heavy aggregations with fixed shapes. PostgreSQL stays the **single source of truth**. Elasticsearch serves the aggregations: total cost by vendor and by item, broken down by department and its units.
3. **Keep the engine replaceable.** Business logic depends on repository interfaces (dependency inversion), not on PostgreSQL or Elasticsearch. Moving a report to another engine, such as ClickHouse, means writing a new repository, not rewriting the use case.

On the front end, I built most of the reporting UI in React and TypeScript:

- **Shareable drill-downs** (dashboard → vendor summary → item detail): filters and period live in the URL, so any view can be bookmarked.
- **Configurable grids:** resize, reorder and hide columns, saved per report type; sorting and filtering run on the server.
- **Saved views:** users keep their own combinations of filters, columns and periods.

### How a user reads a report

The main report, Vendor Performance Summary, works like a funnel. A user starts from the KPI cards, clicks a number to see the vendors behind it, then the items, then every purchase line. The filters chosen once follow the user to every level.

## Data design

Indexing into Elasticsearch runs as a batch job per hospital, in parallel with goroutines, channels and worker pools. Each organization has its own index, rebuilt with fresh data once a day.

## Failure handling

The index is a derived copy. If it is wrong, it can be rebuilt from PostgreSQL by running the indexing job again. While the data is not ready, users see a notice that it is being built, with one option: back to the main system.

## Security

The API uses JWT, and the app shares a single sign-on session with the main platform. Every Elasticsearch query is filtered by tenant.

## Trade-offs

A sync pipeline to run, and the index lags behind the source until the next daily build: changes show up within one day.

## Results

- Dashboard load time <Metric>40s → 1s</Metric>.
- Database CPU <Metric>80% → 30%</Metric> per query.
- The storage engine can change behind an interface without touching business logic.
- <Metric>70+</Metric> front-end test files across the reporting, export and Value Analysis modules.
