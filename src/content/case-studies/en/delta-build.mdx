## Problem

Reports collect data from many sources: invoices, purchase orders, and item and vendor data. Every day the whole dataset was rebuilt from scratch. That took 8 hours and pushed CPU to 90%, even though most of the previous day's data had not changed.

## Approach & alternatives considered

1. **Checkpoint.** Each build saves where it stopped. The next daily run reads only the changes since that checkpoint.
2. **Report items as the unit of work.** The build collects the items that changed, deletes their old report rows, and rebuilds only the current data for those items.
3. **Safe fallback.** When there is no checkpoint yet, such as on the first run, it falls back to a full build.

## Data design

Changes are tracked with history tables for invoice lines and for item and vendor data, a delta flag on changed rows, and sequences with uniqueness triggers.

## Failure handling

- A processing limit keeps a large hospital from overloading the pipeline in one run.
- The full build stays available as the fallback.

## Security

Each run works inside one hospital's own database.
